Contributing to Exam Study Planner

Thank you for your interest in improving Exam Study Planner.

The project is intentionally lightweight and uses plain HTML, CSS and
JavaScript so that it remains easy to understand, test and modify.

Ways to contribute

You can contribute by:

• Reporting bugs
• Suggesting useful study-planning features
• Improving documentation
• Improving accessibility or mobile usability
• Improving the user interface
• Fixing bugs
• Adding tests or validation
• Submitting code improvements

Before making a change

Please check the existing issues and roadmap first where available.

For larger changes, open an issue or describe the proposed change before
starting substantial development. This helps avoid duplicated work and
keeps the project focused on practical exam-preparation needs.

Reporting a bug

When reporting a bug, please include:

1. What you expected to happen.
2. What actually happened.
3. Steps to reproduce the problem.
4. Browser and device used.
5. A screenshot, if useful.

Example:

Problem: Save Mock button is not reachable on a mobile screen.

Steps: 1. Open Mock Tests. 2. Select Record Mock. 3. Enter the test
details. 4. Try to scroll to the Save button.

Device: iPad / Safari

Suggesting a feature

Describe:

• The problem the feature solves.
• How you expect it to work.
• Who would benefit from it.
• Any concerns or alternatives you considered.

Features should preferably support a real study-planning or
exam-preparation need.

Development

The application currently uses:

• HTML5
• CSS3
• Vanilla JavaScript
• LocalStorage

There is no framework or package installation required for the current
application.

The main application is contained in index.html.

Testing changes

Before submitting a change:

1. Open the application in a modern browser.
2. Test the feature you changed.
3. Check the existing major workflows.
4. Test on a small screen where practical.
5. Confirm that existing local data is not unnecessarily lost or
overwritten.

For changes involving LocalStorage, pay particular attention to existing
user data and backward compatibility.

Pull requests

A useful pull request should:

• Have a clear title.
• Explain what changed.
• Explain why the change was needed.
• Mention any relevant issue.
• Include screenshots for visible UI changes.
• Avoid unrelated changes.

Keep changes focused whenever possible.

Code style

Prefer:

• Clear and readable JavaScript.
• Small, understandable functions.
• Descriptive variable names.
• Reuse of existing UI patterns.
• Responsive layouts.
• Accessible labels and controls.

Avoid introducing unnecessary dependencies for functionality that can
reasonably be implemented with the existing technology.

Privacy

Do not introduce features that transmit a user’s study data to an
external service without clearly documenting the change and its privacy
implications.

The current application is designed around local browser storage.
